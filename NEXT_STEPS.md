# Findings and Next Steps

| # | Finding | Evidence | Next Step |
| - | ------- | -------- | --------- |
| 1 | The CasaOS runbook assumes an `x-casaos` metadata block in the compose file, but the current `docker-compose.yml` omits it, so CasaOS imports will miss metadata. | `docs/40-runbooks/casaos.md:12-33`, `docker-compose.yml:2-164` | Decide whether the compose file should include CasaOS annotations or if the runbook needs to be revised, and bring the chosen source of truth into alignment. |
| 2 | Image naming and automation are split between `communityfirst/colmena-app` and `colmena-unified`, creating ambiguous release targets and duplicate build workflows. | `docs/30-implementation/docker-compose.md:6-24`, `docker-compose.yml:112-118`, `.github/workflows/build-and-push.yml:1-71`, `.github/workflows/build-unified.yml:1-169` | Establish the canonical registry image name and retire or repoint workflows and docs that reference the alternate name to prevent drift. |
| 3 | The unified Dockerfile tolerates build failures by generating stub assets (e.g., placeholder HTML and `any`-typed definitions), so CI can succeed while shipping a broken frontend or schema. | `Dockerfile:78-149` | Review the fallback logic and define a guardrail so failed frontend/backend builds surface as blocking issues instead of silently shipping stubs. |
| 4 | CasaOS runbook volume names (`app_data`, `media_uploads`) differ from the compose definitions (`media_data`, `static_data`), risking data loss during migrations or backups. | `docs/40-runbooks/casaos.md:60-63`, `docker-compose.yml:148-177` | Reconcile the documented volume list with the compose file so operators know which volumes to back up and restore. |
| 5 | Backlog items list work that is already implemented (e.g., port cleanup in the test script and Makefile shortcuts), which clouds prioritisation. | `docs/backlog.md:20-24`, `scripts/test-compose-local.sh:42-117`, `Makefile:1-41` | Conduct a backlog grooming pass to close or rescope completed items and keep the queue focused on outstanding gaps. |
| 6 | The Dockerfile defines an extra `frontend-builder-schema` stage that is not consumed in the final image, adding maintenance overhead without benefit. | `Dockerfile:152-175`, `Dockerfile:217-253` | Trace the original intent of the unused stage and either wire it into the build or remove it to simplify future changes. |
| 7 | Building the unified image leaves `schema-runtime.json` empty, so `vite-plugin-pwa` fails to parse it and the build ships a placeholder HTML shell instead of the real PWA bundle. | `Dockerfile:52-108`, `docker build --no-cache --target frontend-builder` log (`RollupError: Failed to parse JSON file /app/frontend/src/api/utilities/schema-runtime.json`) | Ensure the backend OpenAPI export succeeds (or provide a validated fallback) before copying into the frontend so the generated bundle contains real assets. |
| 8 | The emergency OpenAPI stubs declare `Paths`/`Schemas` as plain types, but the frontend treats them as namespaces, producing dozens of TypeScript errors during `npm run build`. | `frontend/src/service/team.ts:1-200`, `frontend/src/pages/User/Configuration/Invitation/InvitationForm.tsx:105-220`, `docker build --no-cache --target frontend-builder` log (TS2702/TS2713 failures) | Regenerate the OpenAPI client or adjust the stubs so namespace access patterns remain valid, preventing the build from degrading to `any` or placeholder assets. |
| 9 | The Nextcloud builder Dockerfile references `FROM nextcloud:$NEXTCLOUD_VERSION-apache`, which BuildKit flags as an invalid default tag when the arg is unset. | `colmena-devops/devops/apps/nextcloud/builder/Dockerfile:1-45`, `docker compose -f docker-compose.local.yml build` warning `InvalidDefaultArgInFrom` | Refine the base image declaration (e.g., use `${NEXTCLOUD_VERSION}` with defaults) so the builder works without manual arg injection and CI stops emitting warnings. |
